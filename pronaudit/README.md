# pronaudit — TTS 발음 결함 자동 탐색

TTS로 합성한 음성을 STT 두 종류에 다시 들려주고, 원문과 자모 단위로 비교해
**발음이 일관되게 무너지는 낱말과 규칙**을 찾아낸다. 오래 켜 두고 아침에
리포트만 보면 되도록 만들었다.

    문항 × 목소리 × take × 샘플레이트 → TTS → [moonshine | whisper] → 자모 비교 → SQLite

## 왜 판정기를 둘 두는가

두 결과를 **합치지 않고 각각 기록한다**. 불일치 자체가 정보이기 때문이다.

| 어디서 틀리나 | 뜻 |
|---|---|
| 둘 다 틀림 | TTS가 실제로 뭉갠 것 — 표기/사전으로 고칠 대상 |
| moonshine만 틀림 | 운용 STT(cpu_stt)가 못 받는 발음. AICC에서 TTS 출력이 STT로 되돌아가는 구조라면 이것도 실전 결함 |
| whisper만 틀림 | 드묾. 대개 whisper 쪽 잡음 |
| 둘 다 맞음 | 정상 |

파일럿에서 실제로 갈렸다. 발음사전을 끈 "함장 하함"을 moonshine은 `함장함.`
으로 받아적었고(= 청취로 찾아낸 그 결함), whisper는 언어모델로 복원해
`함장하함`이라고 적었다. 강한 모델 하나만 썼으면 못 찾았을 결함이다.


## 채점은 표기가 아니라 표면 발음형으로 한다

STT는 *표기*를 뱉는다. TTS가 "조타"를 완벽하게 읽어도 STT는 [조타]를 듣고
훨씬 흔한 "좋다"라고 적는다. 표기끼리 자모를 비교하면 이런 게 전부 100%
오류로 잡히지만 TTS는 아무 잘못이 없다. 첫 12시간 스윕에서 상위 결함 후보의
절반 이상이 이 위양성이었다.

그래서 `phonology.surface()`로 원문과 STT 결과를 **둘 다** 표준 발음법대로
바꾼 뒤 비교한다. 연음·격음화·경음화·비음화·유음화·구개음화·받침 중화·
자음군 단순화와 현대 서울말에서 이미 합류한 모음(ㅐ=ㅔ, ㅚ=ㅙ=ㅞ)을 적용한다.

    좋다 · 조타      → 조타      납부기한 → 납뿌기한 ( "나쁘기한"과는 여전히 다름)
    왜국 · 외국      → 외국      폭뢰 · 폭뇌 → 퐁뇌
    패 · 폐          → 페        갑판 · 가판 → 갑판 · 가판 (진짜 다름 — 남는다)

일부러 적용하지 **않는** 규칙이 둘 있다.

* **ㅎ 탈락** (영향→영양, 하함→하암) — 지금 찾는 결함 그 자체다. 접으면 사라진다.
* **조음위치 동화** (함미→한미) — 표준이 아니고 수의적이다. `loose=True`에서만
  적용해 `동음충돌` 딱지로 따로 표시한다. 소리가 사실상 같으니 판정을 보류한다.

추가로 두 가지를 더 걸러낸다.

* **무판정** — STT가 숫자나 라틴문자를 그대로 되뱉으면(`07시` → `"07시"`)
  TTS가 무엇을 읽었는지 알 수 없다. 정답도 오답도 아니므로 통계에서 뺀다.
* **STT어휘편향** — 최소대립쌍에서 한쪽으로만 쏠리고 반대는 멀쩡하면
  (사외→사회 58/60, 사회→사외 0/60) TTS가 그 소리를 못 내는 게 아니라 STT가
  빈도 높은 낱말을 고른 것이다. 결함 목록에서 내리고 규칙 집계에서도 뺀다.

채점 규칙만 바뀐 경우 합성을 다시 할 필요가 없다. `hyp` 테이블에 STT 원문이
그대로 있으므로 `rescore.py`가 전체 시행을 다시 해석한다 (10460시행 20초).

    ./.venv/bin/python rescore.py --db data/audit.sqlite
    ./.venv/bin/python report.py --top 40


## 설계에서 조심한 것

- **실재하는 낱말만 쓴다.** STT는 없는 말을 들으면 가장 가까운 실재 낱말로
  고쳐 적는다. 무의미 음절을 넣으면 TTS가 잘 읽어도 오답이 나온다.
  최소대립쌍의 짝이 비단어인 것(`하암`, `승암` …)은 `corpus.NONWORDS`에
  묶어 두고 기본적으로 합성하지 않는다 — 방향성 근거로만 쓴다.
- **낱말 단독 발화는 위양성 바닥이 높다.** 파일럿에서 TTS가 제대로 읽은
  "하함"을 whisper가 매번 "하하"로 적었다. 짧고 드문 낱말은 STT의 사전확률이
  음향을 이긴다. 그래서 문항마다 단독 / 문말 / 문두 **세 자리**로 돌리고,
  두 자리 이상에서 무너져야 `발음규칙결함`으로 판정한다. 단독에서만 무너지면
  `단독발화한정`으로 따로 뽑는다(그건 짧은 발화 경로 쪽 문제다).
- **자모 단위로 비교한다.** "확인"이 "황인"으로 들리면 음절 CER은 0.5지만
  실제로 틀린 자모는 하나다. 정도를 과장하면 take 편차와 진짜 결함을
  못 가른다. 편집이 일어난 자리의 앞뒤 자모까지 기록해서, "ㅎ이 사라진다"가
  아니라 "**모음 뒤** ㅎ 초성이 사라진다"까지 나오게 했다.
- **최소대립쌍은 방향을 본다.** `영향→영양`은 3/4인데 `영양→영향`은 0/8이면
  TTS의 ㅎ 탈락이다. 양방향이면 대립 자체가 안 실린 것이고, 한쪽만 빈도 높은
  낱말로 쏠리면 대개 STT의 사전확률이다.
- **8k / 16k를 나눠 잰다.** config의 운용 설정은 8000Hz(전화 음질)라
  ㅎ/ㅅ/ㅊ가 원리적으로 잘 안 실린다. 8k에서만 무너지면 표기로는 못 고친다.
- **결함 후보의 wav만 남긴다.** 이 루프의 산출물은 판정이 아니라
  **들어볼 파일 목록**이다. 최종 확인은 사람 귀로 한다.

## 설치

이미 끝나 있다. 재설치가 필요하면:

```bash
python3.11 -m venv pronaudit/.venv
pronaudit/.venv/bin/pip install sherpa-onnx mlx-whisper soundfile numpy huggingface_hub
pronaudit/.venv/bin/hf download csukuangfj2/sherpa-onnx-moonshine-tiny-ko-quantized-2026-02-27 \
  --local-dir ../cpu_stt/models/moonshine-tiny-ko
pronaudit/.venv/bin/hf download mlx-community/whisper-large-v3-turbo
```

합성은 프로젝트 `.venv`(TTS 쪽)에서 도는 상주 워커(`tts_worker.py`)가 맡는다.
STT 의존성을 TTS venv에 섞지 않으려는 것 — `build.sh`의 PyInstaller 패키징에
쓸데없는 위험을 만들지 않기 위해서다.

## 사용

```bash
cd pronaudit

# 밤새 돌리기 (8시간 뒤 자동 종료, Ctrl+C 로 언제든 중단 가능)
.venv/bin/python run.py --hours 8 --voices all --takes 3

# 아침에
.venv/bin/python report.py --top 40
```

중단해도 안전하다. 다시 돌리면 안 끝낸 조합부터 이어간다. 문항 순서를 고정
시드로 섞어 두어서, 앞에서 끊겨도 모든 축이 고르게 커버된다.

### 자주 쓰는 조합

```bash
# 특정 축만 집중 (문항 id나 축 이름에 부분일치)
.venv/bin/python run.py --only "ㅎ탈락,종성" --takes 5

# 발음 교정 사전 on/off 대조 — 사전에 넣은 교정이 실제로 듣는지 확인
.venv/bin/python run.py --pron both --only "하함" --takes 6

# 후보 선별(best-of-N) 없이 모델 날것의 동작 보기
.venv/bin/python run.py --candidates 1

# 운용 스크립트 문장 투입
.venv/bin/python run.py --extra ../scripts/korean.txt,../scripts/daily.txt

# 계획만 확인
.venv/bin/python run.py --dry-run --voices all --takes 3
```

### 주요 옵션

| 옵션 | 기본 | 설명 |
|---|---|---|
| `--voices` | `M2,F1,M1,F3` | `all` 이면 10종 전부 |
| `--takes` | 3 | 같은 조건 반복 횟수. 클수록 take 편차와 결함이 잘 갈린다 |
| `--rates` | `8000,16000` | `keep` 이면 config 설정 그대로 |
| `--pron` | `off` | `off`(새 결함 찾기) / `on` / `both`(사전 효과 대조) |
| `--candidates` | config값 | best-of-N 후보 수 |
| `--hours` | 무제한 | 이 시간이 지나면 정리하고 종료 |
| `--only` | 전체 | 문항 id/축 부분일치 필터 |

## 리포트 읽는 법

| 판정 | 뜻 | 다음 할 일 |
|---|---|---|
| `발음규칙결함` | 두 판정기 모두, 두 자리 이상에서 붕괴 | wav 듣고 확인 → `config.yaml`의 `pronunciation`에 표기 추가 |
| `전화대역` | 8k에서만 무너짐 | 표기로는 못 고침. `sample_rate: 16000` 검토 대상 |
| `운용STT취약` | moonshine만 틀림 | TTS 출력이 STT로 되돌아가는 경로라면 실전 결함 |
| `단독발화한정` | 단독에서만 무너짐 | `short_candidates` 쪽 문제 |
| `결함의심` | 무너졌지만 근거가 한 자리뿐 | `--only` 로 그 낱말만 반복 시행 |
| `take편차` | 조건에 따라 들쭉날쭉 | 샘플러 문제. best-of-N 영역 |

`■ 자모 혼동 규칙` 절이 규칙 후보다. `C:ㅎ→C:ㅇ` 가 `T:ㅇ _ V:ㅏ` 환경에서
반복해서 나오면 "받침 뒤 ㅎ 초성이 ㅇ으로 흐른다"는 규칙이고, 그게 곧
`pronunciation` 사전에 넣을 표기 후보다.

## 처리 속도

M1 Max 기준 **시간당 약 900건**(합성 3.7s + moonshine 0.16s + whisper 0.4s).
합성이 병목이고, `config.yaml`의 `steps: 16` / `candidates` 설정을 그대로
쓰기 때문이다. 8시간이면 약 7,000건 — 기본 문항 523개를 목소리 4종 ×
2 rate × 3 take로 한 바퀴 도는 데 6,276건이 필요하니 하룻밤에 한 바퀴다.

`cpu_stt`의 WebSocket 서버(`serve.py`)는 쓰지 않는다. VAD와 실시간 페이싱
때문에 발화 길이만큼 기다리게 되고, 여기서는 offline recognizer를 직접
부르면 되기 때문이다.

## 한계

- **자동 판정이 아니라 후보 스크리너다.** 최종 확인은 청취로 한다.
- **음운 변동 축은 감도가 낮다.** TTS가 "신라"를 [실라]가 아니라 [신라]로
  잘못 읽어도 STT는 "신라"라고 적는다. 그 문항들은 `sensitivity=low` 로
  표시해 기본 랭킹에서 빼 두었다(`--show-low` 로 볼 수 있다). 거기서 나온
  오류는 대신 확실한 오류다.
- **8k 판정은 두 STT 모두 16k로 학습된 모델**이라 자체 오류율이 올라간다.
  8k/16k 차이는 절대값이 아니라 **차이**로만 읽어야 한다.
